## Теоретичні відомості

### 1. Як форма передає дані

Браузер формує HTTP-запит, сервер запускає PHP-сценарій, а результат повертається браузеру. PHP працює на сервері: у браузер надходить сформована відповідь, а не вихідний PHP-код.

Атрибут `action` задає адресу обробника, `method` — метод запиту. Атрибут `name` визначає ключ у даних запиту; `id` потрібний для зв’язку з `label`, але не замінює `name`. Вимкнене поле з `disabled` не надсилається. Наявність поля у верстці не гарантує його наявності на сервері.

| Метод | Передавання даних форми | Застосування |
| --- | --- | --- |
| GET | Параметри в рядку запиту URL | Пошук та отримання даних |
| POST | Поля в тілі запиту | Вхід і форма зворотного зв’язку |

POST не шифрує дані: для захисту передавання мережею потрібен HTTPS. Поле `type="password"` лише приховує символи на екрані. Пароль не можна передавати в URL, виводити у відповідь або записувати в діагностичний журнал.

### 2. Суперглобальні змінні та структура введення

Суперглобальні змінні доступні в різних областях видимості PHP без оголошення `global`.

| Змінна | Призначення |
| --- | --- |
| `$_GET` | Параметри рядка запиту, зокрема й у URL POST-запиту |
| `$_POST` | Поля POST-форми з відповідним кодуванням |
| `$_FILES` | Відомості про файли, передані через HTTP |
| `$_SERVER` | Інформація про запит і середовище, зокрема `REQUEST_METHOD` |
| `$_REQUEST` | Поєднання вхідних даних; склад і пріоритет залежать від конфігурації PHP |

Для POST-форми використовуйте саме `$_POST`, щоб джерело даних було явним. `isset()` перевіряє існування значення та його відмінність від `null`, але не доводить, що це непорожній рядок. Оператор `??` дозволяє задати значення за відсутності ключа.

Клієнт може надіслати `login[]=test`, і PHP сформує масив замість рядка. Перед `trim()`, `htmlspecialchars()` або перевіркою пароля перевірте тип через `is_string()`. Значення `"0"` не дорівнює порожньому рядку; для перевірки обов’язковості використовуйте явне порівняння з `''`, а не лише `empty()`.

### 3. Валідація та безпечне виведення

Послідовність обробки: перевірка методу, наявності й типів полів, нормалізація дозволених значень, перевірка правил, формування відповіді. Для імені чи пошти можна прибрати крайні пробіли через `trim()`. Пароль не обрізають і не перетворюють перед перевіркою: пробіли можуть бути його частиною.

HTML-атрибути `required`, `maxlength` і `type="email"` допомагають користувачу, але їх можна обійти. На сервері повторюють перевірки обов’язковості, довжини й формату. `filter_var($email, FILTER_VALIDATE_EMAIL)` перевіряє формат адреси, але не існування поштової скриньки.

Валідація визначає допустимість значення. Екранування робить його безпечним у конкретному контексті виведення. Для тексту HTML та значень атрибутів у лапках використовуйте `htmlspecialchars($value, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')`. Так `<b>Тест</b>` відобразиться як текст. Це захист від XSS у цих контекстах, а не універсальне очищення для JavaScript, URL або SQL.

Після помилки зберігайте екрановані несекретні поля, щоб користувач міг виправити введення. Пароль і поле файла повторно не заповнюйте. Помилка має пояснювати, яке поле виправити; повідомлення про невдалий вхід має бути однаковим для невідомого логіна та неправильного пароля.

### 4. Перевірка облікових даних

Автентифікація перевіряє, ким є користувач; авторизація визначає, які дії йому дозволені. Тут реалізується навчальна перевірка логіна й пароля в межах одного запиту. Повідомлення про успішний вхід саме по собі не створює сеанс і не захищає інші сторінки.

Масив зручно індексувати логіном; запис містить ім’я та хеш пароля. Для створення хешу використовуйте `password_hash($password, PASSWORD_BCRYPT)`, для перевірки — `password_verify($password, $hash)`. Сіль генерується автоматично, тому повторне хешування того самого пароля може дати інший результат. Порівнювати два заново створені хеші не потрібно.

MD5 непридатний для зберігання паролів. Створюйте хеші локально для вигаданих навчальних паролів, а не через онлайн-сервіс. Bcrypt враховує не більше 72 байтів пароля; для вправи задайте межу 8–72 байти й перевіряйте її до виклику функцій. `strlen()` рахує байти, тому кількість українських літер і байтів відрізняється.

Масив у PHP-файлі придатний для вправи, але незручний для реєстрації, зміни паролів і спільного доступу. Базу даних та постійний стан входу в цій роботі реалізовувати не потрібно.

### 5. Поділ програми на файли

`include` і `require` підключають PHP-файл. За відсутності файла `include` видає попередження, а невдалий `require` спричиняє помилку, яка без обробки перериває виконання. Для обов’язкової конфігурації доречний `require`. Шлях будуйте від `__DIR__`, наприклад `$users = require __DIR__ . '/users.php';`; файл `users.php` має повертати масив через `return`.

Обробку запиту розміщуйте перед HTML, форму — в окремому шаблоні, масив користувачів — в окремому PHP-файлі. Не підставляйте дані користувача в шлях підключення. Після рефакторингу повторіть ті самі перевірки: поділ на файли не повинен змінювати поведінку.

### 6. Приймання файла та помилки завантаження

Для поля `<input type="file" name="attachment">` форма повинна мати `method="post"` і `enctype="multipart/form-data"`. У `$_FILES['attachment']` містяться метадані, а сам файл тимчасово зберігається на сервері.

| Ключ | Зміст і правило використання |
| --- | --- |
| `error` | Код результату передавання; перевіряється першим |
| `name` | Клієнтська назва; перед виведенням екранується |
| `type` | MIME-тип, заявлений клієнтом; не доводить тип вмісту |
| `size` | Розмір у байтах |
| `tmp_name` | Тимчасовий серверний шлях; не виводиться користувачу |

Перед читанням ключів перевірте, що запис є масивом, а `error` — цілим числом. `UPLOAD_ERR_OK` означає успішне передавання, `UPLOAD_ERR_NO_FILE` — відсутність файла, `UPLOAD_ERR_INI_SIZE` — перевищення серверної межі, `UPLOAD_ERR_PARTIAL` — неповне передавання. Інші коди також повинні мати зрозуміле повідомлення.

`upload_max_filesize` обмежує один файл, `post_max_size` — усе тіло POST. За перевищення другої межі `$_POST` і `$_FILES` можуть бути порожніми. Це не слід показувати як успіх: повідомте, що дані не отримано, і запропонуйте перевірити розмір запиту. Причину уточнюють за конфігурацією та журналом сервера.

Тут достатньо показати назву, розмір і заявлений тип отриманого файла. Файл не переміщують у постійне сховище, не виконують і не публікують; тимчасовий файл буде прибрано після завершення запиту. Збереження потребувало б додаткових перевірок вмісту та правил доступу, розглянутих у лекції 6.

### 7. Межі прикладу та CSRF

CSRF — це спроба змусити браузер користувача виконати небажаний запит із його повноваженнями. POST не захищає від CSRF. Для форм, що змінюють дані або створюють сеанс входу, застосовують, зокрема, непередбачуваний токен, пов’язаний із сеансом, який сервер перевіряє до виконання дії.

Тут форми лише демонструють перевірку й виведення: вони не надсилають листів, не зберігають повідомлень і не створюють стану входу. Реалізація сесій належить до наступної лабораторної. У висновку поясніть, де потрібна перевірка CSRF-токена, якщо перетворити приклад на справжній сервіс.

## Хід роботи

### 1. Підготовка середовища

1. Переконайтеся, що Apache запущений. Створіть окремий каталог `C:\xampp\htdocs\lab-05`; інші проєкти в `htdocs` не видаляйте.
2. Запишіть версію PHP вебсервера та значення `upload_max_filesize` і `post_max_size`. Перевірте, що `file_uploads` увімкнено. Версія PHP у терміналі може відрізнятися від версії Apache.
3. Відкривайте сторінки через `http://localhost/lab-05/`, а не як локальні файли. Збережіть код у UTF-8.

### 2. Форма й окремий обробник

Створіть `index.php` з наведеною формою. У `login.php` самостійно реалізуйте перевірку POST, типів і непорожності полів. За коректного введення виведіть лише екранований логін і повідомлення «Дані отримано для перевірки». Перевірки облікових даних на цьому етапі ще немає. GET-запит до обробника має показувати підказку перейти до форми без попереджень PHP.

```html
<!DOCTYPE html>
<html lang="uk">
<head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
    <title>Лабораторна робота 5 — вхід</title>
</head>
<body>
    <h1>Вхід</h1>
    <form action="login.php" method="post">
        <p>
            <label for="login">Логін</label>
            <input id="login" name="login" type="text" required>
        </p>
        <p>
            <label for="password">Пароль</label>
            <input id="password" name="password" type="password" required>
        </p>
        <button type="submit">Увійти</button>
    </form>
</body>
</html>
```

У вкладці Network знайдіть метод, адресу запиту та назви полів. Для порівняння створіть тимчасову GET-форму з одним нейтральним полем `query`: поясніть різницю між URL і тілом POST. Використовуйте вигадані дані; пароль не має потрапляти у знімки екрана.

### 3. Обробка в тому самому файлі

Перенесіть обробку до `index.php`, змініть `action` на `index.php`. Відокремте початкове відкриття сторінки від POST за `$_SERVER['REQUEST_METHOD']`. Збирайте повідомлення в масиві `$errors` і показуйте їх біля форми. Збережіть логін після помилки; пароль не відтворюйте.

У [початковому прикладі](src/index001.php) показано таку організацію. Це заготовка отримання даних, яку потрібно доповнити перевіркою користувачів. Основний порядок перевірок:

```php
<?php
$errors = [];
$login = '';
if (($_SERVER['REQUEST_METHOD'] ?? '') === 'POST') {
    $rawLogin = $_POST['login'] ?? null;
    $password = $_POST['password'] ?? null;
    if (!is_string($rawLogin) || !is_string($password)) {
        $errors[] = 'Логін і пароль мають бути рядками.';
    } else {
        $login = trim($rawLogin);
        if ($login === '' || $password === '') {
            $errors[] = 'Заповніть логін і пароль.';
        }
    }
}
```

### 4. Масив користувачів і рефакторинг

1. Створіть не менше трьох вигаданих користувачів із різними логінами та іменами. Масив індексуйте логіном; у кожному записі зберігайте `name` і `password_hash`.
2. Локально створіть bcrypt-хеші навчальних паролів. Генеруйте їх одноразово під час підготовки даних, а не під час кожної спроби входу. Внесіть у масив готові хеші.
3. Установіть для вправи логін із 3–30 символів латиниці, цифр або `_`, пароль — 8–72 байти. Неприпустимі значення відхиляйте до пошуку користувача й перевірки хешу.
4. Знайдіть запис за логіном і перевірте пароль через `password_verify()`. За успіху виведіть екрановане ім’я користувача; за невдачі — «Неправильний логін або пароль». Пароль і хеш у відповідь не виводьте.
5. Винесіть масив у `users.php`, HTML-фрагмент форми — у `login-form.php`. У `index.php` залиште керування запитом і підключення через `require` або `include` з фіксованими шляхами. Поясніть вибір інструкції.
6. Повторіть перевірки після поділу коду. Достатньо процедурного PHP та масивів; класи, реєстрація і база даних не потрібні.

### 5. Завдання для самостійного виконання

Створіть `feedback.php` з формою зворотного зв’язку: ім’я, електронна пошта, повідомлення та необов’язкове вкладення. Обробляйте форму в цьому самому файлі або в окремому обробнику.

| Поле | Вимоги до обробки |
| --- | --- |
| Ім’я | Рядок, обов’язковий після `trim()`, до 100 символів |
| Електронна пошта | Рядок, обов’язковий після `trim()`, до 254 байтів; перевірка `FILTER_VALIDATE_EMAIL` |
| Повідомлення | Рядок, після `trim()` від 10 до 1000 символів |
| Вкладення | Одне, необов’язкове; після успішного передавання розмір від 1 байта до 1 MiB |

Для довжини українського тексту використовуйте `mb_strlen($value, 'UTF-8')`; перевірте доступність розширення `mbstring`. Межі таблиці — умови цієї вправи. Після перевірки всіх полів виведіть безпечно оформлене зведення. Лист надсилати й дані зберігати не потрібно.

Для вкладення перевірте структуру `$_FILES`, код `error`, типи `name`, `type` і `size`, потім розмір. Показуйте тільки назву, розмір та MIME-тип із позначкою «заявлений клієнтом». Відсутність необов’язкового вкладення допустима; помилка завантаження чи порушення межі мають блокувати повідомлення про успішне опрацювання всієї форми.

Якщо POST надійшов без очікуваних даних, повідомте про неможливість опрацювання та можливе перевищення серверного ліміту. Не приховуйте попередження оператором `@`: усуньте причину некоректного доступу до даних.

### 6. Перевірка результату

Виконайте сценарії та запишіть фактичні результати. Негативні запити можна відтворити редагуванням HTML у засобах розробника: приберіть `required` або змініть `name="login"` на `name="login[]"`. Так само перевірте масив замість скалярного поля форми зворотного зв’язку.

| Сценарій | Очікувана поведінка |
| --- | --- |
| Перше відкриття сторінок через GET | Порожні форми без помилок і повідомлення про успіх |
| Правильні дані кожного з трьох користувачів | Повідомлення про успішну перевірку з відповідним ім’ям |
| Невідомий логін; неправильний пароль | Однакове повідомлення про невдалий вхід |
| Відсутнє поле; порожнє значення; масив замість рядка | Зрозуміла відмова без warning, notice або TypeError |
| Логін на 2, 3, 30, 31 символ; пароль на 7, 8, 72, 73 байти | Крайні допустимі значення проходять валідацію, значення поза межами відхиляються |
| Ім’я та повідомлення з українськими літерами | Правильне відображення й підрахунок довжини |
| Неправильна пошта; повідомлення лише з пробілів | Помилка поля; несекретне введення збережено |
| Повідомлення на 9, 10, 1000 і 1001 символ | Відхилення, прийняття, прийняття, відхилення відповідно |
| Повідомлення `<b>Перевірка</b>` | Виведення як звичайного тексту без жирного форматування |
| Коректна форма без вкладення | Успіх і вказівка, що вкладення відсутнє |
| Файл на 1 байт, 1 MiB і 1 MiB + 1 байт | Перші два допустимі, третій відхиляється |
| Порожній файл або код помилки завантаження | Повідомлення про помилку без успішного підсумку |
| POST понад `post_max_size` | Відмова з поясненням, якщо запит дійшов до PHP; можлива відмова вебсервера раніше |

Для перевірки межі 1 MiB серверні ліміти мають дозволяти передавання більшого файла та службових даних форми. Якщо певну помилку неможливо відтворити, позначте сценарій як невиконаний і поясніть відповідну гілку коду; не записуйте вигаданий результат.

Перевірте згенерований HTML початкової сторінки, стану помилки й успішної відповіді через [W3C Markup Validation Service](https://validator.w3.org/). Для локальної сторінки скопіюйте її вихідний HTML у валідатор: PHP-код туди не передають. Виправте помилки розмітки, перевірте зв’язки `label` із полями та доступність кнопок із клавіатури.

## Очікуваний результат і вимоги до якості

Результат — дві локальні форми: перевірка навчальних облікових даних і зворотний зв’язок із показом метаданих вкладення. Обов’язкові ознаки якісного виконання:

- Сервер перевіряє типи, обов’язковість, формат і встановлені межі; некоректне введення не спричиняє попереджень PHP.
- Виведення користувацьких даних екрановане; пароль і хеш не показуються та не записуються в журнал.
- Назви змінних зрозумілі, відступи послідовні, обробка відокремлена від розмітки. Коментарі пояснюють рішення, а не дублюють кожен рядок.
- Помилки дають змогу виправити форму; підсумок успіху з’являється лише після всіх необхідних перевірок.
- Результати перевірок відтворювані, а студент може пояснити шлях даних від HTML-поля до відповіді PHP.

Ці вимоги конкретизують якість виконання завдання. Оцінювання здійснюється за критеріями [робочої програми](../../+РПНД%20WП%202023+.docx); окремої бальної шкали тут не запроваджено.

## Вимоги до звіту

Подайте звіт у PDF та вихідні PHP-файли. Звіт має містити:

1. Тему, мету, фактичну версію PHP, потрібні розширення й ліміти завантаження.
2. Перелік створених файлів із призначенням і коротку інструкцію запуску.
3. Пояснення GET/POST, серверної валідації, екранування та перевірки хешу на прикладі власного коду.
4. Таблицю «сценарій — вхідні дані — очікуваний результат — фактичний результат — висновок» для перевірок вище. Для невиконаних перевірок зазначте причину.
5. Підписані знімки ключових етапів: форма, успішний вхід, помилкове введення, зведення зворотного зв’язку й результат перевірки HTML. Знімки доповнюють, а не замінюють таблицю.
6. Код самостійно виконаного завдання, відповіді на контрольні питання та висновок про виправлені помилки й обмеження прикладу.
