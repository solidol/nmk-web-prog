# Змінні оточення вебсервера

## Мета

Пояснювати передавання конфігурації через оточення процесу, відрізняти її від параметрів запиту та безпечно читати налаштування. Самостійна робота — 2 год.

## Теоретичний матеріал

Змінні оточення — іменовані значення, які процес отримує від середовища запуску. Вони дозволяють використовувати один код із різними налаштуваннями: адресою бази даних, назвою застосунку чи режимом роботи. Значення можуть задаватися оболонкою, службою, контейнером або конфігурацією вебсервера. Це інший канал даних, ніж параметри URL та поля форми.

У PHP `getenv('APP_MODE')` повертає значення змінної або `false`, якщо її немає. `$_ENV` надає масив змінних оточення, але його наповнення залежить від конфігурації PHP. `$_SERVER` містить також відомості про запит і сервер; його не слід сприймати як точну копію оточення. Режими CLI, Apache та PHP-FPM можуть давати різні набори значень.

Значення оточення зазвичай читаються як рядки. Рядок `'false'` при простому приведенні до `bool` не означає логічну хибність. Тому налаштування потребують явного розбору: числа — перевірки діапазону, режими — перевірки за списком, логічні параметри — погоджених текстових значень. Відсутність обов'язкового налаштування краще виявити під час запуску.

```php
<?php
$mode = getenv('APP_MODE');
if ($mode === false) {
    $mode = 'local';
}
if (!in_array($mode, ['local', 'testing', 'production'], true)) {
    throw new RuntimeException('Невідомий режим роботи');
}
echo 'Режим: ' . $mode . PHP_EOL;
```

Приклад читає лише безпечний демонстраційний параметр. Для локального експерименту його можна тимчасово задати через `putenv('APP_MODE=testing')` перед читанням. Така зміна не переписує конфігурацію операційної системи й не є способом постійного налаштування сервера. Потрібно розрізняти тривалість життя процесу та збереження конфігураційного файлу.

Apache має власні засоби передавання змінних, зокрема `SetEnv` і `PassEnv`. Доступність цих значень у PHP залежить від способу інтеграції. Якщо параметр видно в терміналі, але немає у вебзапиті, спочатку порівнюють середовища запуску та налаштування служби. Не слід виправляти таку ситуацію розміщенням пароля безпосередньо в коді.

У Laravel 10 файл `.env` завантажується механізмом конфігурації. Функцію `env()` використовують у файлах `config`, а прикладний код читає `config()`. Після кешування конфігурації Laravel не завантажує `.env` під час кожного запиту; прямі виклики `env()` поза конфігураційними файлами можуть давати неочікуваний результат. Зміни налаштувань мають супроводжуватися відповідним оновленням кешу.

Файл `.env.example` документує назви параметрів із нейтральними значеннями. Справжні паролі та ключі не додають до репозиторію, HTML-відповідей або звітів. Повний вивід `phpinfo()` чи оточення може розкрити службові відомості. Для перевірки достатньо повідомлення про наявність потрібного параметра без показу секретного значення.

## Завдання

1. Виконайте приклад для відсутньої змінної, `testing` і неправильного значення.
2. Поясніть різницю між `getenv()`, `$_ENV`, `$_SERVER` та файлом `.env`.
3. Складіть перелік несекретних параметрів навчального каталогу і вкажіть правила їх перевірки.

## Вимоги до результату

Подайте результати трьох перевірок і схему «оточення — конфігурація — код». Опишіть, чому конфігурація CLI може відрізнятися від вебсервера. Використовуйте лише вигадані значення.
