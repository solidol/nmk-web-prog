# Суперглобальні масиви $_GET, $_POST, $_SERVER

## Мета

Читати параметри HTTP-запиту, перевіряти їхню форму та значення, відокремлювати валідацію від безпечного виведення. Самостійна робота — 2 год.

## Теоретичний матеріал

Суперглобальні масиви доступні в різних областях видимості PHP, зокрема всередині функцій без `global`. `$_GET` містить параметри рядка запиту URL. Назва масиву не означає, що він існує лише для методу GET: адреса POST-запиту також може мати параметри після знака `?`. Для `/courses?page=2` значення `page` зазвичай надходить як рядок.

`$_POST` заповнюється даними POST-запиту з типом вмісту `application/x-www-form-urlencoded` або `multipart/form-data`. JSON-тіло автоматично не перетворюється на цей масив: його читають із `php://input` і декодують окремо. Завантажені файли описує `$_FILES`. Отже, обробник має враховувати метод, тип вмісту та очікувану структуру даних.

`$_SERVER` містить відомості про сервер і поточний запит, наприклад `REQUEST_METHOD` та `REQUEST_URI`. Склад ключів залежить від сервера й способу запуску PHP. Значення, пов'язані із заголовками клієнта, не є автоматично довіреними. Зокрема, User-Agent описує те, що повідомив клієнт, а не підтверджену властивість пристрою.

Перший крок оброблення — перевірка наявності ключа. Оператор `??` дозволяє задати типове значення. Далі перевіряють форму: параметр `page[]=2` може утворити масив замість очікуваного рядка. Лише після цього перевіряють допустимий діапазон. Перетворення на число без валідації здатне приховати неправильне введення.

```php
<?php
$raw = $_GET['page'] ?? '1';
$page = is_string($raw)
    ? filter_var($raw, FILTER_VALIDATE_INT, [
        'options' => ['min_range' => 1, 'max_range' => 1000]
    ])
    : false;
if ($page === false) {
    http_response_code(400);
    exit('Некоректний номер сторінки');
}
echo 'Сторінка: ' . $page;
```

Строге порівняння з `false` відділяє помилку валідації від числового результату. У прикладі дозволені сторінки від 1 до 1000; це навчальне обмеження, яке в реальному каталозі узгоджують із кількістю записів. Відсутній параметр і неправильний параметр обробляються по-різному: перший отримує типове значення, другий спричиняє помилку.

Текстовий параметр перед включенням у HTML екранують функцією `htmlspecialchars()` з відповідним кодуванням. Це не перевірка його змісту й не захист SQL-запиту. Для пошуку в MariaDB значення передають параметром підготовленого запиту або через ORM. POST також не шифрує дані: захищений транспорт забезпечує HTTPS.

Для запитів, що змінюють дані й використовують сеанс користувача, потрібні CSRF-захист та перевірка прав. Об'єднання різних джерел у `$_REQUEST` може приховати походження параметра; для зрозумілого контракту обробника доцільно явно обирати потрібний масив.

## Завдання

1. Перевірте приклад без параметра та з `page=2`, `page=0`, `page=abc`, `page[]=2`.
2. Для кожного випадку запишіть тип отриманих даних, статус і відповідь.
3. Поясніть, де шукати параметр URL, поле POST-форми, JSON-тіло та метод запиту.

## Вимоги до результату

Подайте таблицю перевірок, код і пояснення ролей валідації, екранування та параметризації SQL. Не включайте до звіту повний дамп `$_SERVER` із локальними шляхами чи службовими даними.
