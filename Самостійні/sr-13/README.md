# Абстрактні класи та інтерфейси

## Мета

Розрізняти спільний контракт і спільну реалізацію, обирати між інтерфейсом та абстрактним класом у PHP. Самостійна робота — 2 год.

## Теоретичний матеріал

Інтерфейс описує операції, які має підтримувати об'єкт. У межах PHP 8.1 він може оголошувати публічні методи без реалізації та константи. Клас використовує `implements` і реалізує потрібні методи з сумісними сигнатурами. Клієнтський код може залежати від інтерфейсу, залишаючи спосіб виконання операції конкретному класу.

Абстрактний клас позначають `abstract`; створити його екземпляр безпосередньо не можна. Він може містити стан, конструктор, готові методи та абстрактні методи. Нащадок через `extends` отримує спільну реалізацію і заповнює відсутні частини. Якщо нащадок не реалізує всі абстрактні методи, він також має залишатися абстрактним.

```php
<?php
interface TextReport
{
    public function render(): string;
}

abstract class BaseReport implements TextReport
{
    public function render(): string
    {
        return 'Звіт: ' . $this->body();
    }

    abstract protected function body(): string;
}

class CourseReport extends BaseReport
{
    protected function body(): string
    {
        return 'PHP, MariaDB, Laravel';
    }
}

echo (new CourseReport())->render();
```

У прикладі інтерфейс визначає доступну клієнту операцію `render()`. Абстрактний клас реалізує спільний заголовок, а конкретний клас надає тіло звіту. Метод `body()` захищений, оскільки є внутрішнім кроком побудови. Результат — звичайний текст; для включення довільних даних у HTML потрібне екранування на етапі виведення.

Клас PHP успадковує лише один безпосередній батьківський клас, але може реалізувати кілька інтерфейсів. Тому інтерфейси зручні для незалежних можливостей: об'єкт може бути придатним до експорту й водночас підтримувати журналювання. Не слід створювати великий інтерфейс із методами, які частині реалізацій доведеться залишати порожніми.

Абстрактний клас доречний, коли реалізації справді мають спільний алгоритм або стан. Його використання лише заради кількох однакових рядків може створити зайву залежність між різними сутностями. Альтернатива — композиція: передати окремий об'єкт-помічник через конструктор. Спільний код тоді повторно використовується без нав'язування відношення спадкування.

Сумісність сигнатур включає параметри, тип результату та видимість. Реалізація не повинна звужувати публічний метод інтерфейсу до `protected`. Також потрібно зберігати поведінкові домовленості: формат тексту, порядок даних і спосіб повідомлення про помилку.

У Laravel інтерфейс сховища можна зв'язати з конкретним класом у контейнері сервісів. Контролер отримує контракт, а спосіб доступу до MariaDB залишається в реалізації. Абстрактний клас сам по собі не повідомляє контейнеру, який конкретний нащадок слід створити: відповідність потрібно визначити явно.

## Завдання

1. Додайте другий звіт із власним тілом і перевірте спільний формат результату.
2. Поясніть, чому `new BaseReport()` неможливий, а `new CourseReport()` допустимий.
3. Для експорту каталогу оберіть інтерфейс, абстрактний клас або композицію й обґрунтуйте рішення.

## Вимоги до результату

Подайте код двох реалізацій, результати виконання та схему зв'язків класів. Вкажіть, де визначено контракт, спільний алгоритм і змінну частину. Обґрунтування має спиратися на вимоги задачі.
