# Архітектура MVC у фреймворку Laravel

## Мета

Розподіляти відповідальність між моделлю, поданням і контролером та простежувати оброблення запиту в Laravel 10.x. Самостійна робота — 1 год.

## Теоретичний матеріал

MVC розділяє модель даних і поведінки, їхнє представлення та координацію взаємодії. Model працює з даними й правилами предметної області, View формує представлення, Controller приймає запит і організовує виконання дії. У Laravel ці ролі підтримують моделі, контролери та Blade-шаблони, проте застосунок також використовує маршрути, сервіси й проміжні обробники.

Для сторінки каталогу маршрут `GET /courses` пов'язують із дією контролера. Контролер отримує потрібні курси через модель або сервіс і повертає подання з даними. Шаблон перебирає записи й формує HTML. Браузер не звертається безпосередньо до Eloquent-моделі або MariaDB: він отримує HTTP-відповідь від застосунку.

Нижче — фрагмент методу контролера. Передумови: модель `App\Models\Course`, таблиця `courses` із полями `id`, `title`, налаштована навчальна база та подання `courses.index`. Це схема для аналізу, а не повний застосунок.

```php
public function index()
{
    $courses = \App\Models\Course::query()
        ->orderBy('title')
        ->limit(20)
        ->get(['id', 'title']);

    return view('courses.index', ['courses' => $courses]);
}
```

Eloquent представляє записи як об'єкти й надає засоби запитів і зв'язків. Модель не повинна формувати HTML-картку, а Blade-шаблон — виконувати запит до бази. Обмеження 20 записів у прикладі стримує розмір відповіді, але не забезпечує навігації всім каталогом; для повного списку потрібно спроєктувати пагінацію.

Для створення курсу шлях складніший: маршрут приймає POST, проміжні обробники виконують належні перевірки, вхідні поля проходять валідацію, а контролер викликає операцію збереження. Laravel Form Request може винести правила валідації та перевірку дозволу в окремий клас. Власне правило предметної області має підтримуватися також під час виклику операції з консолі або іншого інтерфейсу.

Контролер не повинен накопичувати всі обчислення. Коли дія координує кілька моделей або транзакцію, її можна винести в сервіс. Водночас для простого читання одного списку зайві проміжні класи не завжди потрібні. Поділ обирають за складністю і повторним використанням, зберігаючи зрозумілий шлях від запиту до результату.

Безпека розподілена між рівнями. Авторизація визначає право користувача виконувати дію; CSRF-захист потрібний для відповідних сеансових запитів. Валідація перевіряє поля, а параметризовані запити ORM відокремлюють SQL від значень. Масове присвоєння потребує явного контролю дозволених полів. Blade екранує текст, який потрапляє в HTML. Жоден із цих механізмів не замінює решту.

Поданням може бути не лише HTML. Контролер API повертає JSON, а модель і сервіси можуть залишатися тими самими. Важливо явно визначити склад відповіді, щоб не розкрити внутрішніх полів. Відокремлення представлення дає змогу додати нового клієнта без дублювання правил роботи з курсами.

Перевірки також розподіляють за відповідальністю: правило моделі перевіряють на допустимих і неправильних значеннях, HTTP-дію — за статусом та доступом, подання — на порожньому наборі й спеціальних символах. Такий поділ допомагає встановити причину помилки.

## Завдання

1. Побудуйте схему GET-запиту каталогу з ролями маршруту, контролера, моделі та подання.
2. Розподіліть дії: перевірка назви, вибірка MariaDB, HTML-екранування, перевірка права редагування.
3. Поясніть, що зміниться, якщо каталог потрібно повертати як JSON.

## Вимоги до результату

Подайте схему і стислий розподіл відповідальності. Назвіть дві помилки архітектури та запропонуйте виправлення. Не потрібно створювати окремий Laravel-застосунок для цього завдання.
