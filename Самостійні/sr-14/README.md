# Створення бібліотеки функцій на основі класів зі статичними методами

## Мета

Організовувати повторно використовувані операції у класі зі статичними методами та визначати обмеження такого підходу. Самостійна робота — 2 год.

## Теоретичний матеріал

Статичний метод належить класу й викликається без створення екземпляра: `ClassName::method()`. Усередині нього немає `$this`, оскільки виклик не пов'язаний із конкретним об'єктом. Такий спосіб доречний для невеликих операцій, результат яких визначають явні аргументи, наприклад перевірки формату або перетворення одиниць.

Бібліотека має об'єднувати споріднені функції, а не всі допоміжні дії застосунку. Назва класу повинна показувати його призначення. Простір імен запобігає конфліктам із класами інших пакетів. Для прикладу створіть файл `Duration.php`; код орієнтований на PHP 8.1+.

```php
<?php
declare(strict_types=1);

namespace Study\Support;

final class Duration
{
    private function __construct() {}

    public static function toMinutes(int $hours): int
    {
        if ($hours < 0 || $hours > 1000) {
            throw new \InvalidArgumentException('Недопустима тривалість');
        }
        return $hours * 60;
    }
}
```

Окремий демонстраційний файл у тій самій папці підключає бібліотеку й викликає метод:

```php
<?php
require_once __DIR__ . '/Duration.php';
echo \Study\Support\Duration::toMinutes(2); // 120
```

Числа тут описують умовну тривалість у звичайних годинах по 60 хвилин; вони не перераховують академічні години дисципліни. Межа 1000 — локальне правило прикладу. Приватний конструктор забороняє непотрібне створення екземпляра, а `final` — успадкування.

Метод не читає суперглобальних масивів, не звертається до бази та не змінює спільного стану. Це робить результат передбачуваним: однаковий допустимий аргумент дає однакове значення. Виняток для неправильного аргументу є частиною контракту, яку викликач має враховувати. Сам метод не вирішує, який HTTP-статус показати користувачу.

Статичні властивості створюють спільний стан класу й потребують обережності. Якщо зберігати в них поточного користувача або параметри запиту, код стає залежним від порядку викликів. Особливо небажаний такий стан у довготривалих процесах. Для роботи з MariaDB або зовнішнім сервісом частіше доречний звичайний об'єкт із явно переданими залежностями.

У проєкті з Composer класи підключають через автозавантаження, зокрема PSR-4: префікс простору імен пов'язують із каталогом. Назва файла й шлях мають відповідати імені класу. `require_once` у прикладі показує мінімальне підключення без зміни конфігурації навчального проєкту. Під час пакування бібліотеки її контракт і вимоги до PHP документують окремо.

Фасади Laravel зовні нагадують статичні виклики, але перенаправляють операції до об'єктів контейнера. Тому їх не слід автоматично ототожнювати з власним класом статичних утиліт. Для вибору підходу потрібно з'ясувати, чи є залежності та змінний стан.

## Завдання

1. Створіть два наведені файли й перевірте аргументи 0, 2, -1 та 1001.
2. Додайте споріднену операцію з чітко описаними одиницями вимірювання.
3. Поясніть, чому підключення до MariaDB недоречно приховувати в цьому класі.

## Вимоги до результату

Подайте файли, результати перевірок і контракт методів. Відокремте повернення значення від його виведення. Опишіть можливе підключення через Composer без зміни конфігурації репозиторію.
